# 功能与机制（中篇）

> 2026-10-20 更新（新增：B站链接自动总结，见 十）。
> 文档中的「下篇」= [docs/03-坑与排错.md](03-坑与排错.md)。

## 一、触发规则（四种）

| 触发 | 要 @ 吗 | 走 LLM 吗 | 说明 |
|---|---|---|---|
| @ 机器人 | 要 | 走 | 正常对话（含图片/视频） |
| 寻呼信标 | 不要 | 不走 | 喊「柴郡柴郡」回「大猪咪」 |
| +1 复读 | 不要 | 不走 | 群里有人复读就跟一次 |
| B站链接 | 不要 | 走（专用引擎） | 群里出现B站视频链接就自动总结（见 十） |

同群 1 秒冷却（共用一个闸门）。不回自己发的消息（防死循环）。
寻呼 / 指令 / @ 我 / B站链接都算「正事」，会打断复读链（复读条件必须排除 bvLink，
否则链接消息被吞进复读分支——2026-10-20 接入时提前避掉的坑）。

## 二、寻呼信标

config.mjs 的 beaconTrigger / beaconReply。喊「柴郡柴郡」回「大猪咪」。
纯脚本、零 token、瞬间到达，目的是让人在群里一搜就定位到机器人。
若同时 @ 了机器人，则信标 + 正常对话都会来。

## 三、+1 复读

有人把上一条原样再发一遍（QQ 会挂个 +1 气泡）时，机器人跟着发一次。

防死循环四道闸：
1. 不处理自己的消息，不会复读自己的复读（永动机直接掐死）
2. 同一内容只跟一次，joined 置位后不再跟，直到群里换了新内容
3. 先置位再发送，发送失败也绝不重试（杜绝「失败重试导致刷屏」）
4. 必须换人重复，同一个人连发同样的话不算 +1

第 2 条里的 joined 在内容不变时会沿用，专门堵「A 发 B 发 A 发 B 发」轮流刷机器人的漏洞。
复读比的是紧挨着的上一条，中间插了寻呼/指令/@/纯媒体/B站链接消息就算换链。

## 四、媒体处理

| 来源 | 图片 | 视频 | 语音 |
|---|---|---|---|
| @ 那条消息里直接附带 | 传 | 传（URL 方式） | 不支持 |
| 回溯群历史（自己发的） | 不传 | 不传（改描述式） | 不支持 |
| 回溯群历史（别人发的） | 不传 | 不传 | 不支持 |

核心：谁发的媒体谁才能让机器人收到，user_id 必须与 @ 者一致。

### 4.1 图片与文字的「关联窗口」（按互动计数）
图片进上下文，但只保留最近 **mediaMemoryWindow(10) 次「与机器人的互动」**；
第 1 条的图到第 11 次互动才不再关联，掉出窗口只剩纯文字。

**群里刷的、不 @ 机器人的闲聊不进上下文，不会把图挤掉。**
窗口是从尾部数 user 条（一条 = 一次和机器人的互动），assistant 回复跟着它所属的互动走。

体积闸 mediaHistoryMaxBytes(8MB)：单个媒体超过它就不进窗口，只在当轮可见。
必要性：若一个大媒体留在窗口里，接下来每次请求都重传它，直接把请求撑爆。

### 4.2 视频走「URL 直传 + 描述式」
视频不再下载转 base64，把 QQ 原始下载链接直接发给模型：

    { type: 'video_url', video_url: { url: <QQ链接> }, fps: 2, media_resolution: 'default' }

依据 MiMo 官方文档（video-understanding）：
- 传入方式两种：URL（公网可访问，≤300MB）或 Base64（base64 字符串 ≤50MB，约等于原片 37MB）
- 格式：MP4 / MOV / AVI / WMV
- fps：抽帧率，默认 2，范围 0.1~10，越高越精细越费 token
- media_resolution：default 平衡档 / max 细节档

URL 方式实测：模型服务方能直接拉取 QQ 的 multimedia.nt.qq.com.cn 链接（带 rkey），
零下载、零转码，也绕开了 base64 50MB 的限制。rkey 会过期，但机器人是拿到立刻就发，时效够用。
拿不到网络链接（本地文件）时才退回 base64 通道（注意 50MB 限制，见下篇坑 29）。

回答完仍要求它写「〔视频描述〕」一句话，系统摘走放进上下文，原片不留 ——
**视频只在被 @ 那一轮可见**，之后模型手里只有那行描述（这是既定设计，防上下文撑爆）。
标记用〔〕而不用尖括号（见下篇坑 11）。
系统提示里也写明：除非用户主动提到视频，否则不要主动提及。

### 4.3 加载失败必须当场说出口
失败原因会直接发到群里，且放在 LLM 之前（万一模型挂了诊断也已送达）：
    [媒体] 视频加载失败（文件 22.0MB 超过上限 100.0MB）
四种情况：超上限 / 下载失败 HTTP xxx / 下载到 0 字节（地址过期）/ 格式不支持。
同时把原因喂给模型，它才能如实说明，而不是瞎猜「一片黑乎乎」。

### 4.4 为什么要回溯
QQ 把「文字+@」和「视频」拆成两条独立消息。第一条带 @ 没视频、第二条有视频没 @，
不回溯就永远看不到视频。
fetchRecentMedia(gid, senderId)：只取最新一条视频，只认本人；
遍历时后出现的覆盖先出现的，天然留最新，所以不要设时间窗口。
不要写「找不到就放宽到任何人」的兜底，那就是别人无关媒体混进来的根源。

### 4.5 格式判断
QQ 媒体的 url 是 multimedia.nt.qq.com.cn/download 这种无扩展名地址，
真实格式要看 file 字段（例如 xxx.mp4）。视频仅接受 mp4/wmv/mov/avi。

## 五、上下文 / 记忆机制

5.1 模型本身无记忆。LLM 是无状态 API，「记忆」是本地拼进请求的：
    messages = [system：人设 + 之前对话摘要]   来自 groupSummary（内存 Map）
             + history：之前所有对话            来自 history（内存 Map）
             + 本次消息
历史必须在 LLM 调用之后再写入，否则同一条消息会同时出现在 history 和 userContent 里，
图片被发两遍、白白双倍计费。

⚠️ **键名统一是命门（坑 28 的教训）**：
history / groupSummary / promptTokens 的键全部是 `group-<群号>` 字符串，
存、取、删任何一处用了裸数字键，上下文就静默失效（机器人变失忆，没有任何报错）。
诊断方法见下篇坑 28。

5.2 全存内存、重启归零。history / groupSummary / promptTokens 都是内存 Map。
重启即失忆、占用 0，这是自洽的不是 bug。

5.3 「上下文」显示的是上次真实请求的 prompt_tokens，不是估算值。
重启后没聊过即 0，每聊一轮跟着更新。不要用估算替代（曾试过，后改回真实值）。

5.4 压缩后不要清零 promptTokens，否则显示假 0、压缩报「到 0」这种误导数字。
压缩拼摘要稿要用纯文字版字段（m.text），因为 m.content 可能是 parts 数组，
直接插字符串会变成 object Object。

5.5 自动压缩：prompt_tokens 达到 contextTokenLimit 乘 compressRatio(0.9) 时触发，
保留最近 keepRecent(6) 条原文，其余压成不超过 300 字摘要注入 system。
可连续压（最多 3 次保护）。手动「压缩」是提前压，不关掉自动压缩。

## 六、消息切分与长度预算

原则：不砍内容、靠预算不靠刀。

6.1 长度预算（让模型自己适配）。lengthHint() 生成「控制在约 2100 字以内」的说明，
作为 extraSystem 传给 askLLM，模型据此自行取舍要点，而不是砍尾巴。

6.2 切分 splitMessage 只负责把已生成好的文本切开发送，不做条数限制、不截断：
先把段落切成不超 chunkChars 的块（超长段落按句子切），再合并短块塞满为止，每条间隔 500ms。
坑：少了合并那一步，短段落会各自成条，再被条数上限硬砍就丢内容。
实测原文 1212 字只发 253 字（丢 80%）。

6.3 markdown 保留（stripMarkdown: false）。回复里的加粗记号是情景模拟的产物，
是表演的一部分，不该清。

## 七、对话线的署名（多人不串线的关键）

history 里每条都带身份：
    用户消息：  张三: 昨晚加班到三点
    柴郡回复：  [回 张三] 又熬夜喵！……

- 用户消息的「昵称: 」前缀在写入时生成；
- 柴郡回复的「[回 昵称]」在回复那一刻从消息事件取昵称拼上（群消息的特殊性：
  回复发到群里，但必须记清当时在回谁，否则多轮插话后模型张冠李戴）。
- 寻呼信标、#指令 不进对话线，无署名问题。

## 八、管理指令（@ + 指令）

| 指令 | 别名 | 走 LLM | 输出 |
|---|---|---|---|
| 上下文 | 记忆 / 查上下文 / ctx / context / history | 不走，零 token | 当前上下文Token 占用：8432 / 120000（7%，压缩阈值 90%） |
| 压缩 | 压缩上下文 / compress / zip | 不走 | 已压缩：46 到 6 条 + 摘要 |
| 清空 | 清空上下文 / clear / reset | 不走 | 已清空 |
| 模型 | 当前模型 / model | 不走，零 token | 当前模型 + 接口 + 思考强度 |
| 吃什么 | 今天吃什么 / 吃啥 / 三餐 / eat / food | 走（调模型） | 早中晚三餐 + 推荐语 |

只有「吃什么」会调大模型，其余全是纯脚本零 token。
不带 # 号也认（整句精确匹配，避免「帮我压缩一下这张图」误触发）。
压缩只报条数不报 token（压缩后真实占用要等下次请求才知道）。

「模型」指令的接口行是从 llmUrl 动态取的主机名（new URL(cfg.llmUrl).host），
以后换服务商它会自动跟着变，不用改代码。
注意：#模型 会报出真实模型名，这是管理指令（走脚本不经模型），
与「聊天里被问模型要装傻」的人设不冲突。

⚠️ **群里没有换模型指令**。换模型是本地管理操作，走「切换模型.cmd」，不开放给群里。

### 8.1 「吃什么」的实现（关键设计）
分工：foods.mjs 真随机抽菜，模型只写推荐语（菜名它碰不了）。
靠提示词让模型「自己随机」不靠谱，实测它每次都往同一舒适区钻。改成脚本抽签后：
- 随机性由 Math.random 保证，不是碰运气
- 自动避开最近推过的 18 道（黑名单）
- 三道全中式时强制补一道西式，保证中西搭配
- 用独立会话 food-群号：不吃群聊记忆、不占上下文额度、不带搜索工具
- 万一模型没按格式输出，抽签结果仍会原样发出去兜底

实测连抽 12 次共 36 道，0 重复。清单 368 道，加菜只需往 foods.mjs 的字符串里用竖线追加菜名。

## 九、网络搜索与网页抓取（走 Exa MCP Server）

搜索走 MCP Server（https://mcp.exa.ai/mcp），实现在 exa.mjs。

### 9.1 为什么走 MCP
- 不需要 API key，实测直接可用，不消耗 Exa 账户额度
- 模型侧照常计费：每次搜索约 1~2k token（生成 query/objective + 读结果）
- 匿名调用的代价：按 IP/会话限流，Exa 随时可能收紧；被限流就在 URL 后加 ?exaApiKey=key

### 9.2 协议要点
JSON-RPC over HTTP（Streamable），响应是 SSE 格式（event: message / data: {...}），
直接按纯 JSON 解析会炸；notifications/initialized 返回空体也要容错。
流程：initialize 握手拿 mcp-session-id，补一条 initialized 通知，然后 tools/list / tools/call。
会话可能被服务端回收，callTool 遇到 error 会自动重新握手再试一次。

### 9.3 工具映射（模型看到的工具名保持不变）
| 模型调用的工具 | Exa MCP 工具 | 参数 |
|---|---|---|
| web_search(query, objective) | web_search_exa | query + objective 都必填 |
| fetch_webpage(url) | web_fetch_exa | urls 数组 |

Exa 要求 query 和 objective 成对给（见下篇坑 23），所以模型的 web_search
工具加了 objective 参数；模型漏填时脚本自动用 query 顶上。

### 9.4 提示词要点
Exa 喜欢语义化描述而不是关键词堆砌：
    好：blog post comparing React and Vue performance
    差：React vs Vue
工具描述里写明 query/objective 都要用英文（Exa 对中文召回极差，
中文问题模型会自动翻成英文，如「上海今天天气」生成 Shanghai weather today）。
常识类问题模型会识别出来不搜，省额度。

### 9.5 自检
自检的「网络搜索」项会真调一次 MCP（约 650 字），exa.mjs 坏了会报
「exa.mjs 加载失败」而不是整个表崩掉（动态导入兜底）。

## 十、B站链接自动总结（bilibili.mjs）

群里出现B站视频链接（BV 号或 b23.tv 短链）**免 @ 自动总结**。链接算「正事」不进复读链。

### 10.1 核心路线：直链直传（零下载零转存）
B站没有官方直链渠道，但播放器自己吃的 **playurl API（platform=html5）返回音画合一
mp4 直链，实测不校验 Referer**（裸拉 206）——可以直接塞 video_url 喂模型：
    view API 拿标题/分P/cid（免登录）
    → playurl API 拿直链（720P，超 290MB 自动降 360P）
    → { type:'video_url', video_url:{url}, fps:2, media_resolution:'default' } 直接喂 MiMo

约束：
- 免登录 720P 封顶（1080P 要 SESSDATA + DASH 音画分离流，不做，总结场景 720P 够用）
- 720P 码率 ≈1.95Mbps → 300MB ≈ 20 分钟；360P ≈ 1 小时
- 直链带 upsig 签名几小时过期 → **现取现喂绝不囤链接**
- 会员/付费/充电视频拿不到 durl，明着报错
- 分P视频每 P 一个 cid，按链接 ?p=N 取对应 P

为什么不用字幕路线：模型「亲眼看片」零转写误差；B站 AI 字幕的专有名词/英文术语
错太多，教程场景一个术语错学到的知识就是错的。

### 10.2 群内编排（bot.mjs 的 handleBilibili）
- **2 小时缓存**：同一视频（BV+P+提问 做键）只看一遍，重发秒回旧总结
- **防重入**：正在看的视频再发不重复点火（双发=双倍烧钱）
- **先发 ack**：看片要几分钟，先回「收到链接」免得群里干等
- **提问识别**：消息里链接之外的话（剔除QQ分享标题【…】和「-哔哩哔哩」后 ≥4 字）
  当作对视频的提问，走问答模式
- **进上下文**：总结以纯文字进对话线（user=「分享B站视频《标题》」、
  assistant=「[回 昵称] 总结正文」），之后群里能接着追问，不重传视频
- **存档**：每次总结落盘 `B站总结\<BV>_P<P>.md`（引擎里做，失败不影响主流程）

### 10.3 引擎与入口共用
核心引擎 `qq-group-bot/bilibili.mjs`：extractBvLink / resolveBV / fetchView /
fetchDirectUrl / summarizeVideo（含拒答检测自动重试，见下篇坑 31）。
命令行入口 `bilibili-summarize.mjs`（仓库根目录）调用同一引擎，只加进度打印。
改链路只改引擎一处。偶发「模型说看不到视频」的坑见下篇坑 31。

## 十一、换模型的运行时覆盖（llmstate.json）

config.mjs 里是默认值；「切换模型.cmd」把新配置写进同目录的 llmstate.json。
config.mjs 末尾在定义完 cfg 之后读这个文件并覆盖字段：

    覆盖字段：llmUrl / llmKey / model / thinking / modelList / llmHeaders

- 文件不存在或 JSON 坏了 → 静默用默认值，不报错、不阻止启动
- 删掉 llmstate.json = 恢复 config.mjs 默认
- 换完模型不用改启动脚本，机器人启动时现读

这个设计的意义：把「代码里的默认」和「运行时选的选择」分开，
换模型不产生代码 diff，改坏了删一个文件就回滚。
注意：`imggen*` / `vidgen*` 的配置（生图/生视频端点和密钥）**不走 llmstate 覆盖**，
换它们只能改 config.mjs 真身（切换模型工具只管 LLM 侧）。

## 十二、文生图：画图意图强制路由（imggen.mjs，2026-10-21 上线）

### 12.1 通道与产物
OpenAI 兼容 `/v1/images/generations` 端点，模型 `gpt-image-2`，返回 b64_json（PNG 约 2~3MB），
OneBot `image` 段 `base64://` 直发群（实测可用；过小/过假的图会被 highway 拒，见下篇坑 33）。

### 12.2 为什么「强制路由」：模型会谎报画好（坑 34）
画图刚上线时出过事故：模型**不调 `generate_image` 工具**，直接模仿上下文里
「画好啦喵～」的成功话术回一句，群里干等图片永远不来。实测提示词劝不住
（模型会「省略步骤演结果」），根治靠脚本接管：

    @ 命中画图句式 → parseDrawIntent 三道门
      → translateDrawPrompt 独立会话翻译成英文 prompt（有否决权：回 NO 放行普通对话）
      → imggen 生图 → 直发群 → ack
    模型全程没有「装成功」的机会。

三道判定门（80 字内，宁漏勿错）：
1. **句头画式**：开头就是「画××」
2. **量词式**：画/生成 + 一/两/三 + 张/幅/个/款
3. **图名词式**：画/生成/来/出 + …… + 图/图片/照片
要的是文字/代码/翻译/**视频**等产物的不接（画图闸与生视频闸互斥——曾发生引用图片
要求「生成小猪视频」被画图路由抢走出了一张图的事故，后补互斥名单）。

### 12.3 改稿路由
画图成功后记 `lastDraw`（prompt/主题/时间）。10 分钟内 @ 发来**短消息带修改语气词**
（改一下/换/重画/不对/错了/性别错了/不像……）——这种话没有画图句式、过不了三道门，
会被当普通聊天处理，模型又只承诺不干活。改稿路由接住：带上次 prompt + 修改点
走改稿模式翻译重新生成。

### 12.4 防谎报闸（兜底，不依赖路由）
即使走普通对话，askLLM 出口也有检测：本轮没调过 `generate_image` 但回复含
「画好/画完/图片已生成/这就画/马上画」→ 注入系统提示打回重画。
工具失败时脚本**直接把失败原因发到群里**（不只进日志——曾翻车：审核拦截只记 bot.err，群里干等）。

### 12.5 中转的脾气（都要如实转告）
- **审核过敏**：正常内容也可能被 400 拦（卡通猫都拦过）；暴力向描述必拦
- **429 限流**：读 Retry-After 等待重试一次，再不行明说
- **Key 可能被停用/限额打满**（API_KEY_DISABLED / QUOTA_EXHAUSTED）：如实报错，
  去服务商控制台恢复
- 连画多张建议隔 1-2 分钟

## 十三、文生视频 / 图生视频（vidgen.mjs，2026-10-21 上线）

### 13.1 通道与协议
生视频中转（与生图同站、**独立 Key 独立计费**），异步任务制：

    POST /v1/videos/generations        → { request_id }
    GET  /v1/videos/<request_id>       → { status: pending/done, progress }（5s 一拍）
    GET  /v1/videos/<request_id>/content → mp4 成片（8s ≈ 5.5MB）

模型 `grok-imagine-video-1.5`：通道文档标称只支持图生，**实测 prompt-only 也能出片**。
生成是分钟级，路由接管前先发 ack（「要几分钟，别干等～」）。

### 13.2 触发与图生视频
触发双闸：@ + 含「视频/影片/动画」+ 含生成类动词（且长度 80 字内）。
与画图闸互斥（见 12.2）。翻译会话 `vid-<群号>` 独立，可否决放行普通对话。

**图生视频**：消息本体或引用里的图 → 提交时 `image_url` = data URL 字符串。
实测坑位（探测浪费了一把额度换来的）：`image`=纯 base64 → 422 拒；
`image_url`=对象 → 502；`image_url`=**字符串 data URL** → 200 通。

### 13.3 限制与闸门
- **15 秒上限**：`vidgenMaxSeconds`（默认 15），成片 done 后硬检查 `duration`，
  超限弃用不发（费用照扣，但绝不让超长片进群）；提交不带 duration 走自动时长（≈8s）省额度
- **下载自动重试**：done 后下载遇 429/5xx/超时/0 字节重试最多 4 把
  （有 Retry-After 按它等）——任务已完成、费用已扣，不让一次限流白扣额度
- **业务总闸 `vidgenEnabled`**（默认 true）：false 时 @ 点视频直接回「暂停营业」，
  **不进普通对话**（防坑 34 族：模型承诺「这就生成」却零动作）
- 提交对 502/503/504/超时重试 2 次（中转网络波动实测 502）
- ⚠️ request_id 只存在于内存和日志，重启即失、中转无列表接口——
  下载彻底失败的成片找不回来，只能重新生成
